## החיבור: אחד לכל לשונית
- **WebSocket אחד ללשונית**, לכתובת ה-Realtime של הפרויקט (`SUPABASE.url` עם `/realtime/v1/websocket`, וה-anon key), לכל המקורות והערוצים של הדף. כל מקור הוא הצטרפות לערוץ (`phx_join`) על אותו חיבור, לא חיבור נוסף.
- **הרשאה:** הטוקן של המשתמש מ-`FLOA_AUTH.token()`, בהצטרפות. כשהטוקן מתחדש, לפני שהוא פג, הקיט שולח `access_token` לכל ערוץ פתוח. בלי התחברות: ה-anon key, ורק מה ש-RLS מרשה לאנונימי. יציאה מהחשבון סוגרת את החיבור ומרוקנת את המקורות.
- **פעימה** כל 25 שניות. שתי פעימות בלי תשובה: החיבור נחשב מת, נסגר ונפתח מחדש.
- **חיבור מחדש:** המתנה שגדלה (שנייה, 2, 4, עד 30 שניות) עם מעט אקראיות, כדי שכל הלקוחות לא יחזרו באותה שנייה. בחזרה כל ערוץ מצטרף שוב.
- **השלמה:** אחרי חיבור מחדש, חזרה לרשת (`online`) וחזרה ללשונית, **כל מקור פעיל נטען מחדש בשקט** (אותה בקשה של הטעינה הראשונה), כי מה שקרה בזמן הניתוק לא יגיע בזמן אמת. התוצאה עוברת דרך העדכון לפי מפתח, ולכן מה שלא השתנה לא נוגעים בו, וזה **פרץ** ("אפקטים": בלי אפקט לכל פריט).
- **ברקע:** לשונית מוסתרת שומרת את החיבור עד 5 דקות (קבוע של הקיט) ואז סוגרת אותו, כדי לא להחזיק חיבור של הפרויקט. בחזרה: חיבור והשלמה.
- **בלי רשת:** הרכיבים נשארים עם מה שיש, לא עוברים למצב טעינה ולא לריק. מצב החיבור כתוב ב-`data-live` על `html` (`on`, `connecting`, `off`), וזה האות לאפליקציה שיש לה מצב לא מקוון משלה. אין הודעה על כל ניתוק.
- **כמה לשוניות:** לכל לשונית חיבור משלה, והיא מקבלת את השינויים בעצמה, גם את מה שנכתב בלשונית אחרת של אותו אדם. הטוקן כבר משותף (`floa.session` ב-`/auth.js`). חיבור אחד לכל הלשוניות (לשונית מובילה ו-`BroadcastChannel`) לא נדרש עכשיו, ונכנס רק אם מספר החיבורים מתקרב לגבול ("גבולות").

## מקור: `RosterLive.source`
```js
var tasks = RosterLive.source({
  table: "tasks",                        // או rpc: "<שם>", args: { … }
  select: "id,title,note",               // ה-select של REST, כולל צירוף
  filter: { list_id: id },               // שוויון אחד בזמן אמת ("גבולות"); חל גם על הבקשה
  order: "created_at.desc",
  key: function (r) { return r.id; },    // המפתח הראשי של הטבלה
  watch: [{ table: "task_tags", filter: { list_id: id }, key: function (r) { return r.task_id; } }],   // טבלאות נוספות שמשנות את התוצאה
  map: function (r) { return r; }        // לא חובה
  // schema: ברירת המחדל SUPABASE.schema; live: false רק עם סיבה
});
tasks.rows()  tasks.get(key)  tasks.status  tasks.on(fn)  tasks.refetch()  tasks.write(key, patch, run)  tasks.close()
```
- **מה הוא עושה:** טוען (REST של `table` או `rpc`, דרך `FLOA_AUTH.api`), נרשם ל-`postgres_changes` (הוספה, עדכון ומחיקה) של `table` ושל כל טבלה ב-`watch`, ושולח למאזינים שינויים לפי מפתח: `{ rows, added, changed, removed, moved, origin }`. `origin` הוא `remote` (אדם אחר, מכשיר או לשונית אחרים), `local` (כתיבה שלי, "כתיבה מיידית") או `sync` (טעינה ראשונה והשלמה).
- **מצבים (`status`):** `loading` (`rows()` מחזיר `null`), `live`, `stale` (מנותק, או שההצטרפות נדחתה; השורות האחרונות), `failed` (הטעינה הראשונה נכשלה).
- **הצטרפות שנדחתה:** השרת דוחה הצטרפות בשתי דרכים: תשובה `phx_reply` עם `error`, או `ok` ואחריה הודעת `system` עם `status: "error"` (למשל "Unable to subscribe … invalid column for filter"). בשתיהן המקור לא נשאר `live` כשלא מגיע אליו כלום: הוא עובר ל-`stale` (דרך אותו `on` ואותו `status`), וטוען את עצמו מחדש בשקט כל 30 שניות (`T.poll`) כשהלשונית נראית, וגם בחזרה ללשונית. בחיבור הבא הוא מנסה להצטרף שוב, והצטרפות שהצליחה מחזירה `live` ועוצרת את הטעינה החוזרת. ב-localhost גם אזהרה בקונסול.
- **איך שינוי נכנס:**
  - **טבלה אחת בלי צירוף:** השורה מהאירוע נכנסת במקומה לפי המפתח (דרך `map`), בלי בקשה.
  - **צירוף או `rpc`:** האירוע הוא רק סימן. המקור טוען מחדש את השורה של המפתח כשהוא ידוע (`key` של ה-`watch`), ואחרת את כל הבקשה. אירועים שמגיעים יחד מתאחדים לבקשה אחת (300ms).
  - **מחיקה** מגיעה עם המפתח הראשי בלבד ("צד השרת"). המקור מוציא את השורה שהמפתח שלה תואם, ומתעלם ממפתח שאין אצלו.
- **מקור משותף:** שני רכיבים שמבקשים מקור זהה (אותם `table` או `rpc`, `select` ו-`filter`) מקבלים את אותו אובייקט, עם ספירת שימושים. רכיב שיצא מהדף משחרר אותו, ומקור שאין לו משתמשים עוזב את הערוץ.
- **RLS:** הטעינה והשינויים עוברים באותו טוקן ובאותו RLS. מה שהמשתמש לא רשאי לקרוא לא מגיע אליו גם בזמן אמת. אין דרך שנייה לדאטהבייס.

## כתיבה מיידית: `source.write`
- **`source.write(key, patch, run)`:** הקיט מחיל את `patch` על השורה מיד ומודיע לרכיבים (`origin: "local"`, חוק "תגובה מיידית"), ו-`run()` שולח לשרת ומחזיר Promise. מפתח חדש הוא הוספה; `patch` שהוא `null` הוא מחיקה. בזמן ש-`run` רץ, הפריט מסומן `aria-busy` כמו ב-`list.busy`.
- **ההד:** השינוי שלי חוזר מה-Realtime. אירועים לאותו מפתח בזמן ש-`run` רץ נשמרים בצד, וכשהוא נגמר הקיט מחיל את האחרון מהם, או את מה שהשרת החזיר (`prefer: "return=representation"`). שורה זהה למה שכבר מוצג לא מגיעה לרכיב בכלל: אין החלה כפולה, אין הבהוב ואין אפקט שני.
- **כישלון:** השורה חוזרת למה שהייתה, עם האפקט ההפוך (פריט שנוסף יוצא, פריט שהוסר חוזר), וההודעה של האפליקציה אומרת למה (`ui/docs/toast.md`).
- **שמירה של עמודה, לא של שורה:** שדה שומר רק את העמודה שלו, כדי ששני אנשים בשני שדות של אותה שורה לא ידרסו זה את זה. הכתיבה האחרונה שמגיעה לשרת קובעת.

## רכיבים
- **רשימה:** `RosterList.render(el, source, opts)`. כשה-`items` הוא מקור, הרשימה נרשמת אליו בעצמה: `loading` הוא מצב טעינה, `failed` הוא `list.fail(source.refetch)`, וכל שינוי הוא `update` לפי מפתח עם כל מה ש"עדכון בלי ציור מחדש" כבר מבטיח (פוקוס, גלילה, פריט בשימוש מחכה), ועם האפקטים. `opts.where(row)` ו-`opts.sort(a, b)` מסננים וממיינים אצל הלקוח, בלי מקור שני. `destroy` משחרר את המקור. **אפשרויות `remove.run` ו-`sortable.onMove` עוברות דרך `source.write`.**
- **כרטיס פתוח, כותרת, צ'יפ, השם בתפריט האפליקציה, "מתנגן עכשיו":** `RosterLive.bind(el, source, key, fn)`. `fn(row)` מחזיר טקסט, והקיט כותב `textContent` רק כשהטקסט השתנה, עם אפקט השינוי. כותרת נמדדת מחדש לבד (`RosterHeader.fit` כבר שומע שינוי תוכן). שורה שנמחקה: `fn(null)`, והאפליקציה מחליטה מה קורה למסך (בדרך כלל חזרה עם הודעה: "מישהו אחר שינה את מה שפתוח", `ui/docs/toast.md`). בנגן חי רק הטקסט (שם, מבצע); מה שמתנגן ואיפה הוא לא נתון של הדאטהבייס.
- **ספירה ותג:** נגזרים ממקור, לא נשאלים לבד: `RosterLive.bind(el, source, null, function (rows) { return rows.length; })` (`key` שהוא `null`: כל השורות). המונה במפריד של רשימה (`count: true`) כבר נגזר מה-`items`.
- **גוף של קטע:** רשימה משלו עם מקור משלו (`filter` לפי הקטע). גוף עצל (`lazy`) נרשם כשהוא נבנה, ומשחרר כשהקטע יוצא מהדף.
- **שדה וטופס:** שדה בלי כפתור שמירה הוא שדה בעריכה משותפת (`RosterField.live`, "עריכה משותפת" למטה). שדה בטופס שנשלח בכפתור מקבל את הערך ההתחלתי מהמקור, ומה שכתוב בו לא נדרס כל עוד החלון פתוח.
- **טופס עם כפתור שמירה: בדיקה בשמירה (החלטת הבעלים, 2026-11-26, אפשרות ב).** חל על כל טופס שנשמר בכפתור בקיט (`RosterSheet.confirm` עם `fields`, וכל טופס אחר עם "שמירה").
  - **החלון זוכר את מה שהוא נפתח איתו:** לכל שדה, הערך ששמור בשרת ברגע הפתיחה (ו-`rev` של השורה כשיש).
  - **השמירה מותנית:** `PATCH ?id=eq.<key>&<עמודה>=eq.<הערך בפתיחה>` (או `&rev=eq.<n>`, או פונקציה שבודקת את אותו תנאי), עם `prefer: "return=representation"`. שורה חזרה: נשמר, והחלון נסגר כרגיל.
  - **אף שורה לא חזרה:** מישהו שינה בינתיים. הקיט טוען את הערך הנוכחי ושואל בחלון הקצר שלו, מעל הטופס (`RosterSheet.confirm`, העוגן הוא כפתור השמירה): הכותרת היא השאלה, עם מי ומה, למשל "עדכון של הדר: השדה שם השתנה ל«מפגשים בתנועה». לשמור את שלך במקומו?" (ערך ריק לא מצוטט: "נמחק" או "מולא", `ui/docs/window.md`), והפעולה "שמירה". **שמירה:** כתיבה בלי תנאי, שדורסת. **סגירה:** לא נשמר, הטופס נסגר, והמסך מראה את הערך של האדם האחר (הוא כבר במקור החי). כמה שדות שהשתנו: משפט אחד שמונה אותם.
  - **שם האדם:** מי ששינה אחרון, כשהטבלה שומרת אותו (`updated_by`); אחרת "בינתיים השדה <תווית> השתנה ל«<ערך>»". בלי פועל בגוף של האדם.
  - הטופס לא כותב תנאי ולא שאלה בעצמו: `RosterSheet.confirm` עושה את זה כשהשדות שלו מגיעים עם `source`, `key` ו-`col` (או `save` שמחזיר `{ conflict: { value, by } }`).
- **נוכחות (מי כאן ומי כותב איפה):** `RosterLive.presence(topic, { item, field })` על **ערוץ פרטי** (`private: true`) של הדבר הפתוח, בשם `<schema>:<טבלה>:<מזהה>`. נשלחים רק מזהה המשתמש, השם הקצר שלו, הפריט, השדה ומקום הסמן כמספרים: לא אימייל. הטקסט של שדה בעריכה משותפת עובר באותו ערוץ רק בזמן הקלדה ("הקלדה חיה" למטה). מתעדכן לכל היותר כל 120ms, ונוכחות שלא חודשה 6 שניות יורדת. **נוכחות נראית רק כסמנים בתוך שדה בעריכה משותפת (הבעלים, 2026-11-26):** אין שורת "מי כאן" בכותרת או בשום מקום אחר, ואין צבע לכל אדם.

## עריכה משותפת
(הבעלים, 2026-11-26: עריכה משותפת היא יכולת של הקיט, כמו בשדות "פואטיקה" ו"הנחיה" של ביודנסה היום: טקסט חי בין עורכים, הסמנים של אחרים עם השם, ושמירה בלי כפתור.)
- **איזה שדות:** **כל שדה שעורך נתונים משותפים ואין לו כפתור שמירה הוא שדה בעריכה משותפת, כברירת מחדל:** שורה אחת, רב שורות וטקסט עשיר. לא: שדה בטופס שנשלח בכפתור (חלון קצר עם "שמירה"), חיפוש, ושדה שהערך שלו אישי ולא משותף (הוא עדיין חי ונשמר בלי כפתור, אבל בלי סמנים של אחרים).
- **API:**
  ```js
  RosterField.live(ctl, source, key, col, { delay, empty, toValue, fromValue });
  ```
  `ctl` הוא הפקד שבתוך `.rfield` (`input`, `textarea` או `.rf-rich`). `col` היא העמודה בשורה `key` של `source`. `toValue` ו-`fromValue` (לא חובה) ממירים בין הטקסט בשדה לערך בעמודה (למשל ריק שפירושו "ירושה מהקטלוג" שנשמר כ-`null`). האפליקציה לא כותבת שמירה, מיזוג, סמן, נוכחות או תור.
- **הערך של טקסט עשיר:** טקסט רגיל, שורה חדשה היא `\n`, ומודגש הוא `**…**`. זו הצורה שנשמרת, שמתמזגת ושנשלחת, אף פעם לא HTML. הקיט ממיר בין הצורה הזאת לתוכן של `.rf-rich` (היום `rtWalk` ו-`rtHtml` של ביודנסה, שעוברים לקיט).
- **מודל המיזוג: מיזוג תלת כיווני של טקסט, עם שמירה מותנית (הבעלים, 2026-11-26, אפשרות א).** לכל שדה יש **בסיס**: הערך האחרון שהשרת אישר.
  - **הגיע ערך מבחוץ ואני לא משנה את השדה:** הוא נכתב במקום, עם אפקט השינוי, והסמן שלי (אם אני בשדה) נשאר באותו מקום בטקסט.
  - **הגיע ערך מבחוץ ואני משנה את השדה:** הקיט מחשב מה הם שינו מהבסיס ומה אני שיניתי מהבסיס (השוואה לפי תווים, טווח אחד או כמה), ומחיל את שלהם על שלי. טווחים שלא נוגעים זה בזה: שניהם נשארים. טווחים שחופפים: שלי נשאר בתוך החפיפה, ושלהם מחוצה לה. **הסמן והבחירה שלי עוברים דרך השינוי** (טקסט שנוסף לפני הסמן מזיז אותו קדימה באותו מספר תווים), והטקסט שלהם מופיע במקומו בלי הבהוב. הבסיס החדש הוא הערך שהגיע.
  - **השמירה מותנית:** הקיט שולח את הערך הממוזג רק אם השורה עוד בגרסה שהבסיס שלי בא ממנה (עמודת `rev` שטריגר מעלה בכל עדכון, ו-`PATCH ?id=eq.<key>&rev=eq.<n>`). אף שורה לא התעדכנה: מישהו שמר בינתיים. הקיט טוען את השורה, ממזג שוב ושולח שוב, בלי שום דבר על המסך.
  - **למה זה ולא CRDT או פעולות:** הטקסטים קצרים (פסקה או כמה), מעט עורכים יחד, והשרת הוא טבלה רגילה עם RLS. מיזוג תלת כיווני נותן "שניהם נשמרים" בכל מה שלא חופף, לא צריך שרת ולא היסטוריה של פעולות, ועובד עם אותו REST. CRDT היה מחייב מבנה נתונים בעמודה ושרת שמבין אותו, ו"האחרון קובע" על כל השדה מוחק את מה שאחר הקליד באותו זמן, וזה בדיוק המקרה של עריכה משותפת.
  - **מודגש אחרי מיזוג:** זוג `**` שהמיזוג שבר (אחד בלי השני) יורד, כדי שלא יישאר סימן גלוי בטקסט.
- **הקלדה חיה: המילים עוברות בערוץ, הדאטהבייס הוא האמת (הבעלים, 2026-11-26: "אין פה ממש הקלדה שוטפת של הצד השני").** קודם המילים עברו רק דרך השמירה, והשמירה מחכה ל-`delay` אחרי ההקשה **האחרונה**, ולכן מי שמקליד ברצף לא נראה אצל אחרים עד שהוא עוצר, ואז עוד הלוך חזור לשרת, אירוע `postgres_changes` וטעינה של השורה (במקור עם צירוף עוד 300ms). נמדד בשני דפים עם רשת מדומה: חציון 3.5 שניות. עכשיו:
  - **שליחה:** בכל הקשה השדה שולח את הערך שלו, עם מקום הסמן, ה-`rev` של הבסיס שלו, מזהה אקראי של הלשונית ומספר שעולה בכל הודעה, **באותו ערוץ פרטי של הנוכחות** (`presence.text`, אירוע `txt`), לא בערוץ חדש. לכל היותר הודעה כל 60ms, וההודעה האחרונה תמיד יוצאת. המטען: מזהה המשתמש, השם הפרטי ואות ממשפחה (כמו בסמן), הפריט, השדה, הערך, הבסיס והסמן. לא אימייל. הערך מוגבל לאורך של השדה (`maxLength`), ולכל היותר 20000 תווים; ערך ארוך יותר לא נשלח בערוץ ומגיע רק דרך השמירה. רגע לפני שמירה השדה שולח את מה שהוא שומר, כדי שההד שלה לא יזיז כלום אצל אחרים.
  - **קבלה:** הודעה של הלשונית שלי, או עם מספר ישן או חוזר מאותה לשונית, נזרקת. השאר מתמזג במיזוג התלת כיווני, כשהבסיס הוא מה שאותה לשונית שלחה קודם (כבר על המסך שלי), ואחרי הפסקה הערך השמור. הסמן, הבחירה ומחסנית הביטול שלי עוברים דרך השינוי, והסמן שלהם זז עם המילים. שינוי זהה משני הצדדים (הם כבר קיבלו את המילים שלי) נספר פעם אחת. באמצע מילה של IME ההודעה מחכה לסוף המילה.
  - **השמירה לא השתנתה:** מושהית, מותנית ב-`rev`, ורק אחרי עריכה אמיתית. **כל אחד שומר רק את מה שהוא הקליד:** מילים של אחר שהגיעו בערוץ לא גורמות לי לשמור, גם לא ב-`blur` ובסגירה.
  - **ההד מהדאטהבייס מתיישב בשקט:** הד שהטקסט שלו כבר הגיע בערוץ (או שהשולח כבר על `rev` חדש יותר ממנו) מזיז רק את הבסיס, לא את המסך: בלי הבהוב, בלי קפיצת סמן ובלי החלה כפולה. הד אחר עובר בדרך הרגילה למעלה. שדה שאף אחד לא מקליד בו 4 שניות, ושאין בו שינוי שלי שלא נשמר, חוזר לערך השמור, כך שמילים שנשלחו בערוץ ולא נשמרו אף פעם (למשל השולח התנתק) לא נשארות על המסך.
  - **בלי ערוץ:** ערוץ פרטי שנדחה (RLS), ניתוק או בלי התחברות: `presence.text` מחזיר `false`, לא נשלח כלום, והשדה עובד בדיוק כמו קודם, דרך השמירה וההד. בלי הודעה.
  - **עלות:** הודעה לכל הקשה (עד כ-16 בשנייה למקליד) נספרת במכסת ההודעות של הפרויקט ("גבולות"). סמן שכבר יצא עם המילים לא נשלח שוב כ-`cur`.
  - **נמדד (2026-11-26, שני דפים, רשת מדומה):** 40 תווים ב-10 תווים לשנייה. לפני: חציון 3516ms, p95 5646ms. אחרי: חציון 44ms, p95 50ms, שמירה אחת בלבד לדאטהבייס, בלי קפיצת סמן אצל השני.
- **הסמנים של אחרים:** בשדה שיש בו עוד מישהו, `RosterField.live` מצייר סמן לכל אחד (`.rpeer`, ה-markup של הקיט, שכבה מעל הטקסט שלא תופסת לחיצות) במקום שלו בטקסט, עם השם הפרטי שלו (ואות ממשפחה כשלשניים אותו שם פרטי), ובחירה שלו כרקע שקוף. **הצבע: `--accent-2` לכולם, צבע אחד, והשם על הסמן הוא מה שמבדיל בין אנשים (הבעלים, 2026-11-26).** הבחירה של אחר: `--accent-2-tint`. אסור צבע שמחושב בקוד (`hsl`) ו-`style` מ-JS. סמן שלא חודש 6 שניות יורד.
- **נוכחות בשדה:** מי שהפוקוס שלו בשדה. כשיש עוד מישהו בשדה, ה-`label` של השדה נשאר כמו שהוא, והשם של כל אחד הוא על הסמן שלו. בלי רשימת אנשים נוספת בשדה.
- **שמירה אוטומטית:** `input` עם השהיה (`delay`, ברירת מחדל 700ms), ו-`blur` מיד. רק העמודה הזאת נשלחת. ערך שלא השתנה מהבסיס לא נשלח. **שמירה רק אחרי עריכה אמיתית** (הקלדה, או שינוי שלי מהתור): חיבור לשורה, ציור מחדש ושדה חדש במקום ישן לא כותבים אף פעם, ושורה לא נוצרת לערך ריק (`ui/docs/field.md`). כך שרשרת של שמירה, עדכון מהמקור, ציור מחדש ושדה חדש לא הופכת לסערת כתיבות.
- **מצב השמירה (שקט):** כשהכול נשמר אין שום סימן, כי זה המצב הרגיל (ו"נשמר" לא נכתב, `ui/docs/toast.md`). המצב כתוב ב-`data-save` על `.rfield` (`pending`, `offline`, `failed`), ו-CSS מציג רק את החריגים בשורת המצב (`.rf-note`): `offline`: "יישמר כשהחיבור יחזור"; `failed`: "לא נשמר", עם ניסיון חוזר לבד בחיבור הבא.
- **בלי חיבור:** השדה נשאר עריך. מה ששיניתי נשמר בתור של הקיט במכשיר (`localStorage`, `floa.live.q`, לפי טבלה, שורה ועמודה, עם הבסיס), כך שגם רענון לא מאבד אותו. כשהחיבור חוזר: טעינה של השורה, מיזוג תלת כיווני מול הבסיס ששמור בתור, ושמירה מותנית. **אפליקציה שיש לה מצב לא מקוון שלם** (בלי שרת בכלל, מעותק במכשיר) יכולה להחליט שהשדות שם לקריאה בלבד; זו החלטה שלה, מוצהרת.
- **ביטול (Ctrl+Z) נשאר מקומי:** הוא מבטל רק את מה שאני הקלדתי, לא את מה שאחרים כתבו. הקיט מחזיק מחסנית משלו לכל שדה (מיירט `historyUndo` ו-`historyRedo` של `beforeinput`), כי כתיבה מקוד מבלבלת את המחסנית של הדפדפן. כל צעד שלי מועבר דרך השינויים של אחרים שנכנסו אחריו, כמו הסמן.
- **בועת עיצוב (מודגש):** עובדת כמו בכל שדה (`ui/docs/format-bubble.md`). מודגש הוא שינוי בטקסט (`**`) ולכן מתמזג כמו כל שינוי. הבועה לא נסגרת ולא זזה כשמגיע שינוי מבחוץ, והבחירה שלה עוברת דרך השינוי כמו הסמן.
- **כיוון ועברית:** המקומות נספרים בתווים של הטקסט השמור, לא בפיקסלים ולא בצמתים של ה-DOM, ולכן הם זהים אצל כל עורך. השדה `dir="auto"` כמו היום, ושום דבר לא מוסיף תווי כיוון (`U+200E`, `U+200F`) לטקסט. סמן שנופל בין עברית לאנגלית מצויר במקום הלוגי שלו, ושם הוא נשאר.
- **אפקטים:** שינוי מבחוץ בשדה שאני **לא** בו: הערך החדש ואפקט השינוי ("אפקטים"); בהקלדה חיה פעם אחת לרצף ההקלדה, לא בכל הקשה. בשדה שאני **בו**: הטקסט של אחרים מופיע במקום שלהם, ליד הסמן שלהם, **בלי** הבהוב, כי הסמן שלהם כבר אומר מי ואיפה.
- **ביודנסה (נעשה, 2026-11-26):** העוזרים של טקסט עשיר עברו ל-`RosterField.rich`; פואטיקה, הנחיה, הערות והפתיחה (הטקסט החופשי ופסקה של כל מוביל) הם `RosterField.live`, עם הסמנים של הקיט בערוץ הפרטי `biodanza:vivencia:<מזהה>`; "נשמר" לא נכתב. נשאר כהחלטה מוצהרת שלה: בלי חיבור (`state.offline`, המצב הלא מקוון השלם) השדות לקריאה בלבד.
- **שדות שעוברים מחלון עם כפתור לעריכה במקום (הבעלים, 2026-11-26):**
  - **עוברים לעריכה במקום מעיפרון, בעריכה משותפת (נעשה):** הנושא של ויוונסיה (העיפרון אחרי הכותרת; `namePopup` נשאר רק ליצירה) ושם התרגיל (העיפרון אחרי השם, בכותרת במחשב ובלשונית בטלפון; `itemNameDialog` נמחק).
  - **נשארים בחלון עם כפתור שמירה, עם "בדיקה בשמירה":** יצירה של ויוונסיה חדשה, שם ומבצע של שיר (`songEdit`), שם מלא בחשבון (`accountDlg`), ושינוי שם של משתמש בניהול (`userEditDlg`).

## עריכה במקום מעיפרון (שם של דבר)
(הבעלים, 2026-11-26. **זה מצב של `ui/docs/field.md`** (שדה במקום, בלי חלון), שמתארח בחריץ הכותרת של **`ui/docs/header.md`** ושל **`ui/docs/card.md`**. לא רכיב חדש: כפתור אייקון, שדה, ו-`RosterField.live`.)
- **מה זה:** שם של דבר (נושא, שם של פריט) שמוצג ככותרת ונערך במקום שבו הוא מוצג: בלי חלון, בלי כפתור שמירה, בשמירה אוטומטית ובעריכה משותפת.
- **הכפתור:** כפתור אייקון שקט (`.rbtn.rbtn--icon.rbtn--muted`) עם הסמל `edit` של הערכה, מיד אחרי הטקסט של השם, `--gap-tight` ממנו, בתוך החריץ של הכותרת. `aria-label` ו-`title`: "עריכת <מה>" (למשל "עריכת הנושא"). מוצג רק למי שרשאי לערוך. בכותרת הוא חלק מהחריץ של הכותרת, לא פעולה, ולכן לא מתקפל ל"עוד" (`RosterHeader.fit` סופר אותו עם הכותרת).
- **רק העיפרון מתחיל עריכה.** לחיצה על השם עצמו עושה מה שהיא עושה בהקשר שלה (בוחרת לשונית, פותחת כרטיס, כלום), והחלקה על השם היא של מי שמחזיק את ההחלקה. כך אין התנגשות בין עריכה לבין בחירה או החלקה, והתנהגות אחת בטלפון ובמחשב. החלקה שמתחילה על העיפרון לא מתחילה החלקה, ובזמן עריכה ההחלקה של המכל כבויה.
- **עריכה:** לחיצה על העיפרון מחליפה את הטקסט של השם, באותו מקום, בשדה שורה אחת של הקיט (`.rfield` בלי מקום תווית, התווית ב-`aria-label`), **באותה טיפוגרפיה של השם שהוא מחליף** (אפשרות של השדה, `.rfield--inline`, `font: inherit`), כך ששום דבר לא קופץ. העיפרון מוסתר בזמן העריכה, הפוקוס בשדה והסמן בסוף. השדה מחובר ב-`RosterField.live` לעמודה של השם: שמירה אוטומטית, מיזוג וסמנים של אחרים.
- **סיום:** `blur` או Enter. השדה חוזר להיות טקסט, והפוקוס חוזר לעיפרון. Escape: חוזר לערך שהיה כשהעריכה התחילה (שמירה אחת של הערך הזה) ומסיים. שם שחייב ערך ונשאר ריק: חוזר לערך הקודם, בלי שמירה.
- **אצל אחרים:** השם מתעדכן חי, עם אפקט השינוי ("אפקטים"). בזמן שאני בעריכה, פריט ברשימה שהשם שלו בעריכה הוא "בשימוש" ולא מוחלף ("עדכון בלי ציור מחדש").
- **API (מומש, 2026-11-26):** `RosterField.inline(btn, textEl, source, key, col, { required, label })`. הקיט עושה את ההחלפה, הפוקוס, הסיום ואת `RosterField.live`. האפליקציה כותבת רק את הכפתור ליד השם.
- **אסור:** לחיצה על השם שפותחת עריכה, חלון עם כפתור שמירה לשם משותף, ושדה במקום בגודל אחר מהשם.

## אפקטים: הוספה, הסרה, שינוי והזזה
(הבעלים, 2026-11-26. אוצר תנועה אחד לכל הקיט. **האפקטים שייכים לרכיבים** וממומשים פעם אחת: בעדכון לפי מפתח של `RosterList`, ב-`RosterLive.bind` וב-`RosterField.live`, ובעוזר משותף אחד, `RosterMotion.flip`. אפליקציה לא כותבת אפקט.)
- **הוספה:** הפריט החדש נכנס במקומו. השכנים מפנים לו מקום בהחלקה (FLIP: מודדים לפני ואחרי, ומזיזים ב-`transform` מהמקום הישן לחדש), והפריט נכנס ב-`opacity` מ-0 וב-`transform` קטן (כמו פתיחה של קטע, `@starting-style`).

## נגישות
- **הכרזה מנומסת, ורק כשרלוונטי:** באזור ה-`aria-live="polite"` שכבר יש לרשימה (של ההסרה והסידור). רק הוספה והסרה **של אחרים** ברשימה שעל המסך, מאוחדות לשתי שניות למשפט אחד ("נוספו 2 פריטים", "<שם> הוסר"). לא על ההד שלי, לא על השלמה, לא על שינוי תוכן, ולא על כל פעימה. בשדה: שורת המצב (`.rf-note`) פעם אחת לכל רצף שינויים.
- **פוקוס לא זז בגלל שינוי מבחוץ,** חוץ מפריט שבפוקוס שנמחק (הכלל של "מקלדת" ב-`ui/docs/list.md`). בזמן האפקט הפריט נשאר לחיץ ובר פוקוס; פריט שיוצא כבר לא.
- **אף פעם `role="alert"`** לשינוי חי.

## צד השרת: מתכון לכל אפליקציה
(SQL רץ רק באישור מפורש של הבעלים, לכל קובץ. הסוכן כותב את הקובץ ומציג.)
1. **publication:** כל טבלה שמקור קורא או מאזין לה (`table` ו-`watch`) נכנסת ל-`supabase_realtime`, בבלוק שבודק קודם ב-`pg_publication_tables` (הצורה: `apps/biodanza/realtime.sql`). טבלה שלא שם לא שולחת כלום, בלי שגיאה. לכן `ui/live.js` כותב אזהרה בקונסול ב-localhost כשמקור חי לא קיבל אף אירוע וטבלה שלו לא מופיעה בבדיקה של הסוכן.
2. **replica identity:** ברירת המחדל (המפתח הראשי) מספיקה. תחת RLS, אירוע מחיקה נושא רק את המפתח הראשי גם עם `full`, ולכן `full` לא נותן כלום לטבלאות שלנו (כולן עם RLS) ורק מכביד על הלוג. **לא שמים `full`.** מה שכן צריך: שה-`key` של המקור יהיה המפתח הראשי של הטבלה, ובמפתח מורכב שהוא יכלול את מזהה ההורה (למשל `(vivencia_id, who)`).
3. **RLS קובע גם את זמן האמת:** לכל שינוי, ה-Realtime בודק את מדיניות הקריאה מול כל מאזין. לכן מדיניות קריאה זולה: פונקציית עזר עם אינדקס (כמו `can_view`).
4. **סינון:** מסנן אחד לכל הרשמה (`eq`, `neq`, `lt`, `lte`, `gt`, `gte`, או `in` עד 100 ערכים). **מחיקה לא מסוננת:** היא מגיעה לכל מי שמאזין לטבלה, עם המפתח בלבד. לכן מפתחות הם `uuid` שאין בהם מידע.
5. **נתונים מצורפים ו-`rpc`: איזו דרך, מתי:**
   - **ברירת המחדל: מאזינים לטבלאות הבסיס (`watch`) וטוענים מחדש** את המפתח שהשתנה או את הבקשה. פשוט, אותה דרך קריאה, ו-RLS נכון מעצמו.
   - **שידור מטריגר** (`realtime.broadcast_changes` או `realtime.send` לערוץ פרטי, עם RLS על `realtime.messages` לפי `realtime.topic()`), רק כש: (א) הרבה מאזינים על אותם נתונים בבת אחת (עשרות ומעלה, למשל מסך של אירוע חי), כי בדיקת ה-RLS לכל מאזין לכל שינוי רצה בתהליך אחד; (ב) השינוי צריך להגיע למי שלא רשאי לקרוא את שורת הבסיס (ספירה, סיכום); (ג) מחיקה צריכה יותר מהמפתח. זה SQL לכל טבלה, ולכן רק כשבאמת צריך.
6. **ערוצים פרטיים לנוכחות ולשידור:** `private: true`, ומדיניות RLS על `realtime.messages` לפי שם הערוץ (`select`: מי רשאי לשמוע; `insert`: מי רשאי לשלוח), אותה שאלה של `can_view`. בלי זה כל מי שיש לו את ה-anon key ואת שם הערוץ שומע ושולח.
7. **טבלה שיש בה שדה בעריכה משותפת:** עמודה `rev bigint not null default 0`, וטריגר `before update` שמעלה אותה באחד, בשביל השמירה המותנית ("עריכה משותפת"). טבלה שיש לה טופס עם כפתור שמירה יכולה לקבל גם `updated_by uuid` (אותו טריגר, `auth.uid()`), כדי שהשאלה של "בדיקה בשמירה" תאמר מי שינה.

## גבולות ועלויות
- **חיבורים:** חיבור לכל לשונית פתוחה, **וכל האפליקציות של הדומיין חולקות את הגבול של פרויקט אחד** (לפי התוכנית: בחינם בערך 200 חיבורים בו זמנית ו-100 הודעות בשנייה; ב-Pro בערך 500 ו-500; לבדוק בדאשבורד). הסגירה ברקע שומרת על המספר. חריגה ב-Pro מחויבת לפי שיא החיבורים וההודעות.
- **ערוצים:** עד 100 לחיבור. המקורות המשותפים שומרים על מספר קטן; דף עם יותר מ-20 מקורות הוא סימן לתכנון לא נכון.
- **טבלאות שנכתבות בקצב גבוה** (היסטוריה, לוגים, מונים) לא נכנסות ל-publication. מקור עליהן הוא `live: false` עם הסיבה.
- **אחרי פרסום:** החיבור יוצא ישר מהדפדפן ל-`wss://` של Supabase, מכל כתובת של הדומיין, ובלי שינוי ב-Worker. Service worker לא נוגע ב-WebSocket. אם יום אחד תיכנס CSP, היא צריכה `connect-src wss://<project>.supabase.co`.

## ממסר חי בשרת שלנו
(הבעלים, 2026-11-26: התנועה בין עמיתים, כלומר הקלדה חיה (`txt`), סמנים (`cur`) ונוכחות, עוברת דרך השרת שלנו, ה-Worker של `api.floa.co.il`, ולא דרך שידור של Supabase. הסיבה: Supabase בתוכנית החינמית, 100 הודעות ו-100KB בשנייה **לכל הפרויקט**, וחריגה מנתקת את כל החיבורים של הפרויקט, גם של roster ושל שאר האפליקציות. **ממומש (2026-11-26), לא פרוס:** `ui/live.js`, `worker/src/live/`. צד השרת: `worker/LIVE.md`. מה שהמימוש עשה אחרת מהטקסט כאן כתוב ב"מה המימוש עשה אחרת" בסוף הסעיף.)
- **מה נשאר ב-Supabase:** כל מה שהוא נתונים. `postgres_changes` (המקורות, `RosterLive.source`; רק עד שלב 3, ולאפליקציה שלא ב-`SUPABASE.relayData`), הכתיבות, השמירה המותנית, התור וה-RLS. **הדאטהבייס הוא האמת, והממסר לא שומר כלום:** לא טקסט, לא סמן ולא נוכחות. מה שעובר בממסר הוא רק מה שעבר עד היום בערוץ הפרטי של הנוכחות.
- **חדר:** כל ערוץ נוכחות (`RosterLive.presence(topic)`) הוא **חדר** בממסר, לפי אפליקציה ומזהה: `<app>/<id>`. הנושא `<schema>:<טבלה>:<מזהה>` של היום ממופה לחדר אחד: האפליקציה היא הסכמה, והמזהה הוא המזהה של הדבר הפתוח. איזה מזהה מותר ואיזו שאלת הרשאה חלה עליו נקבע בשרת, ברשימה של חדרים לכל אפליקציה (`worker/LIVE.md`), ולא בדפדפן.
- **מעבר (transport) אחד מתוך שלושה, לכל חדר, והאפליקציה לא יודעת איזה:**
  1. **הממסר** (`relay`): ברירת המחדל, כשהדומיין הגדיר כתובת ממסר (`SUPABASE.relay` ב-`/supabase.js`, למשל `wss://api.floa.co.il/live`).
  2. **שידור של Supabase** (`broadcast`): הדרך של היום, באותו ערוץ פרטי. רק כשאין כתובת ממסר מוגדרת. זה המתג לאחור: הסרה של הכתובת מחזירה את הדרך הישנה בלי לגעת בקוד.
  3. **בלי חי** (`none`): מה שקורה היום כשהערוץ נדחה. `P.text` מחזיר `false`, אין סמנים, והשדה עובד דרך השמירה וההד בלבד.
  - **ממסר שלא זמין לא נופל לשידור של Supabase** (ממתין להחלטת הבעלים, ראו למטה): הוא נופל ל-`none`, וממשיך לנסות להתחבר בהמתנה שגדלה. שתי סיבות: (א) חדר מפוצל, שבו לשונית אחת בממסר ואחרת בשידור, הוא חדר ששני אנשים בו לא רואים זה את זה, וזה גרוע משקט; (ב) נפילה של הממסר הייתה מחזירה בבת אחת את כל העומס ל-Supabase, בדיוק המקרה שהממסר בא למנוע.
  - **הממשק של `RosterLive.presence` לא משתנה:** `text`, `onText`, `live`, `ok`, `set`, `clear`, `peers`, `on`, `attach`, `close`, באותן חתימות ובאותה צורה של הודעה (`{ uid, first, tab, seq, item, field, v, r, a, b }`). `RosterField.live` לא יודע מאיזה מעבר הגיעו המילים. `P.transport` (קריאה בלבד: `relay`, `broadcast` או `none`) נחשף בשביל בדיקות.
- **חסכוני, כחוק (הבעלים, 2026-11-26: "יחסית חסכוני"):** כל הכללים בסעיף הזה נבחרו כדי שכל הודעה תהיה קטנה ושלא תצא הודעה שאין בה צורך. אלה דרישות, לא המלצות:

  - **`cur` רק כשהסמן באמת זז**, לכל היותר 4 בשנייה (250ms), ו**בלי חזרות תקופתיות**: השרת יודע מי מחובר, וסמן נשאר עד שהוא זז, עד יציאה מהשדה או עד `leave`. סמן שכבר יצא עם `txt` לא נשלח שוב.
  - **שקע נפתח רק כשיש בשביל מה:** אדם מחובר, ועל המסך שדה בעריכה משותפת (לפחות `attach` אחד בחדר). מסך בלי עריכה משותפת לא פותח שקע בכלל. השדה האחרון שיצא סוגר את השקע אחרי 10 שניות (כדי שמעבר בין לשוניות של אותו עורך לא יפתח ויסגור).
  - **השרת לא שומר טקסט**, לא בודק הרשאה בכל הודעה, ושולח את אותה הודעה, מקודדת פעם אחת, לכל השאר.
- **החיבור לממסר: WebSocket אחד ללשונית**, לכתובת `<relay>/<app>/<id>` של החדר הפתוח. זה חריג מוצהר לחוק "חיבור אחד ללשונית": החיבור של Supabase נשאר אחד ונושא את הנתונים, והממסר הוא שרת אחר. היום יש בדף לכל היותר חדר עריכה אחד פתוח (הוויוונסיה או התרגיל הפתוחים); מעבר לחדר אחר סוגר את השקע הקודם ופותח חדש. **אם יום אחד יידרשו שני חדרים בבת אחת**, הם עוברים על אותו שקע (ריבוב לפי חדר, שינוי בשרת), ולא בשקע שני.
- **הרשאה:** ההודעה הראשונה בחיבור היא הטוקן של המשתמש (`FLOA_AUTH.token()`), לא בכתובת, כדי שטוקן לא ייכתב בשום לוג של כתובות. בלי התחברות אין חיבור לממסר (כמו היום: נוכחות רק למחובר). כשהטוקן מתחדש (אותה בדיקה של `T.token`), הקיט שולח את החדש. השרת מאמת את הטוקן מול Supabase ושואל את שאלת ההרשאה של החדר בטוקן של המשתמש עצמו **רק בחיבור ובחידוש טוקן**, ושומר את התשובה לשקע; לא בכל הודעה. הוא **חותם בעצמו** את מזהה המשתמש ואת השם (`u`, `n`, `g`; `g` היא האות ממשפחה, כי `f` הוא השדה) על כל הודעה שהוא מעביר. מה שהדפדפן שולח בשדות האלה נזרק.
- **סוגי הודעות** (שמות קצרים; הצורה המלאה ב-`worker/LIVE.md`):
  - **מהדפדפן:** `auth` (הטוקן ו-`s`, מזהה הלשונית), `txt` (שינוי, למטה), `cur` (`i` הפריט, `f` השדה, `a`, `b`; `f: null` הוא יציאה מהשדה), `rs` (בקשת התיישרות מלשונית אחרת) ו-`ping`.
  - **מהשרת:** `ok` (אחרי הרשאה: מי אני ומי כבר בחדר), `join` ו-`leave` (נוכחות: אדם נכנס לחדר, או שהלשונית האחרונה שלו יצאה), `txt`, `cur` ו-`rs` של אחרים, חתומים, ו-`pong`.
  - **`txt` הוא שינוי, לא ערך:** `q` המספר העולה (הלשונית `s` נאמרת פעם אחת ב-`auth`, והשרת מוסיף אותה להודעה), `bq` המספר שהשינוי נבנה עליו, `i` הפריט, `f` השדה, `p` המקום, `d` כמה תווים נמחקו שם, `x` הטקסט שנכנס, `r` ה-`rev` של הבסיס, ו-`a`, `b` הסמן. טווח אחד (מה שבין התחילית המשותפת לסיומת המשותפת), ולכן הקשה היא כמה עשרות בתים. **ערך מלא** (`v` במקום `p`, `d`, `x`, ובלי `bq`) רק: בהודעה הראשונה של רצף הקלדה (אחרי `SETTLE` בלי הקלדה, כי אז המקבלים כבר שכחו את הבסיס של הלשונית), כתשובה ל-`rs`, ורגע לפני שמירה כשהערך השמור שונה ממה שנשלח. **מי שהצטרף** (`join`) עוד אין לו בסיס לאף לשונית, ולכן השינוי הראשון שהוא מקבל מכל מקליד מביא `rs` אחת וערך מלא אחד; משם רק שינויים.
  - **הקבלה:** הקיט שומר לכל לשונית, פריט ושדה את הערך האחרון שבנה ואת המספר שלו. שינוי שה-`bq` שלו הוא המספר הזה מוחל עליו, והתוצאה (ערך מלא) עוברת ל-`onText` כמו היום, ומשם למיזוג התלת כיווני. פער (`bq` אחר) או לשונית לא מוכרת: השינוי נזרק, ונשלחת `rs` אחת ללשונית ההיא (לכל היותר אחת בשנייה לכל לשונית), שעונה בערך מלא. **`RosterField.live` לא יודע על השינויים:** הוא נותן ל-`P.text` ערך מלא ומקבל ב-`onText` ערך מלא; הקידוד והפענוח הם של `presence`.
  - **השרת לא מחזיר הודעה לחיבור ששלח אותה.** ללשונית אחרת של אותו אדם היא כן מגיעה (בדיוק כמו היום: המילים שלה, בלי סמן שלי), והקבלה עדיין זורקת מספר ישן או חוזר מאותה לשונית. `rs` עובר רק לשקע של הלשונית `s` שהתבקשה.
  - `leave` מוריד את הסמן של אותו אדם מיד. **אין יותר תפוגה של 6 שניות (`T.stale`) לסמן בממסר**, כי אין חזרות: סמן יורד ב-`cur` עם `f: null`, ב-`leave`, או כשהחדר יוצא מ-`relay`. `join` לא מצייר כלום (אין שורת "מי כאן"); הוא רק מצב.

- **הממסר לא מעביר נתונים, רק סימן (`chg`):** איזו טבלה, באיזו עמודת מפתח, אילו מפתחות, איזה `rev` ואיזו פעולה. המקור שמחזיק את המפתח טוען את השורה בעצמו, ב-REST, בטוקן שלו ומבעד ל-RLS, באותה דרך של "צירוף או `rpc`" היום (`touch`, מאוחד ל-300ms). לכן בממסר אין תוכן, ואין בו דרך לקבל שורה שאסור לקרוא: מה ש-RLS לא מרשה חוזר ריק, והמקור מוציא את המפתח אם החזיק אותו. **כל סימן הוא טעינה, אף פעם לא החלה עיוורת,** גם במחיקה: מפתח של ויוונסיה הוא גם המפתח של שורת הבעלים שלי וגם של שורת בעלים של אדם אחר, ורק הטעינה יודעת מה מהן נמחקה.
- **ההודעה:** `{ t: "chg", tb, o, kc, c }`. `tb` הטבלה; `o` הפעולה (`i`, `u`, `d`); `kc` עמודת המפתח שהסימן מדבר בה (`id`, `vivencia_id`, `item_id`); `c` רשימה של `[מפתח]` או `[מפתח, rev]`, עד 50, או `"*"`, שפירושו "משהו בטבלה הזאת בחדר השתנה", והמקור נטען כולו.
  - **מפתח נשלח רק כשהוא `uuid` שאין בו מידע.** מפתח שיש בו אימייל או שם (בביודנסה: `who` של הפתיחה, והאימייל של מוביל בפריט) לא נשלח. אז `c` הוא `"*"`, והמקור הקטן של החדר נטען כולו.
  - בלי אימייל, בלי טקסט ובלי ערך של עמודה. הודעה טיפוסית: 80 עד 200 בתים.
- **שני מסלולים לאותו סימן:**
  1. **מהלקוח:** אחרי כתיבה שהצליחה דרך הקיט (`source.write`, `RosterField.live`, `remove.run` ו-`sortable.onMove` של רשימה, `RosterSheet.confirm` עם מקור, וכתיבה דרך `RosterLive.rest`), הקיט שולח `chg` בשקע של החדר, עם ה-`rev` שחזר בתשובה (`return=representation`) כשיש. השרת חותם עליו כמו על `txt` ומעביר לכל האחרים בחדר. כתיבה שנכשלה לא שולחת כלום. האפליקציה לא שולחת `chg` בעצמה.
  2. **מהדאטהבייס:** טריגר **ברמת הפקודה** (`for each statement`: קריאה אחת לפקודה, לא לשורה) על כל טבלה חיה שולח `POST /live/notify` ל-Worker דרך `pg_net`, עם סוד משותף. ה-Worker ממפה לחדרים ומפיץ `chg`. זה מכסה כל כתיבה שלא עברה בקיט: ה-API הציבורי, דף ניהול, האפליקציה הישנה שעוד מפורסמת, ו-SQL ידני.
- **פעם אחת, לא פעמיים:** כתיבה של הקיט שתוכרז בשקע נושאת את הכותרת `x-floa-live: 1` (ואם בדיקת ה-CORS של Supabase דוחה כותרת חדשה, אותו סימן בתוך `prefer`: `floa-live`), והטריגר מדלג עליה. הקיט שם את הכותרת **רק כשהשקע מאושר** (`ok`) ברגע שהכתיבה יוצאת. `chg` שלא יצא (השקע נפל בין הכתיבה לשליחה) נשמר בתור קטן בזיכרון של הלשונית, ויוצא מיד אחרי ה-`ok` הבא. כך כל כתיבה מוכרזת פעם אחת: מהלקוח כשאפשר (מהיר, ו-20 סימנים כאלה הם בקשה אחת), ומהדאטהבייס בכל מקרה אחר.
- **ואם בכל זאת הגיע פעמיים (מותר ולא מזיק):** `[מפתח, rev]` שהמקור כבר מחזיק באותו `rev` או חדש ממנו נזרק בלי בקשה. מפתח בלי `rev` (טבלה בלי `rev`) מתאחד ב-300ms של `touch` לבקשה אחת. סימן על מפתח שאני כותב עכשיו (`pending`) עובר לדרך של ההד שמחכה, כמו היום.
- **ההד שלי:** הסימן לא חוזר לשקע ששלח אותו, והטריגר מדלג על הכתיבה שלי. מה שהשרת החזיר בכתיבה (`return=representation`) הוא ההד, כמו היום. לשונית אחרת שלי מקבלת את הסימן כמו כל אחד (`origin: "remote"`).
- **חדרים:**
  - **מקור מצהיר על החדר שלו:** `RosterLive.source({ …, room: <מזהה> })` (בביודנסה: המקורות של הוויוונסיה הפתוחה, `room: id`). מקור בלי `room` שייך ל**חדר הבית של האפליקציה**, `<app>/home`.
  - **שקע אחד ללשונית, בחדר אחד** (הכלל של שלב 1 לא משתנה): החדר של הדבר הפתוח, כשיש מקור חי עם `room`; אחרת חדר הבית. זה אותו שקע של הנוכחות וההקלדה: בוויוונסיה פתוחה שקע אחד נושא `txt`, `cur` ו-`chg`.
  - **`chg` חל על כל מקור של אותה אפליקציה** שה-`table` שלו, או טבלה ב-`watch` שלו, היא `tb`, גם מקור ששייך לחדר אחר ועדיין חי (למשל השם של הוויוונסיה הפתוחה, שמגיע ממקור של רשימת הבית). הדאטהבייס שולח שינוי בשורה של ויוונסיה גם לחדר שלה וגם לחדר הבית, ולכן המסך הפתוח שומע אותו.
  - מקור של חדר שהלשונית לא בו (רשימת הבית בזמן שוויוונסיה פתוחה) לא שומע שינויים שקורים רק שם. כשהלשונית חוזרת לחדר שלו, הוא נטען פעם אחת ("השלמה"). מה שלא על המסך לא צריך להיות חי.
  - **השקע נפתח עכשיו לכל מקור חי** של אפליקציה שהנתונים שלה עברו לממסר (`SUPABASE.relayData`), אצל אדם מחובר, ולא רק לשדה בעריכה משותפת. שאר כללי השקע של שלב 1 נשארים: סגירה אחרי 30 שניות של הסתרה, פעימה, המתנה שגדלה.
- **רשימות הבית (ויוונסיות, בעלים, שיתופים): חדר אחד לאפליקציה, לא חדר לאדם.** חדר לאדם (`user/<uid>`) היה מחייב שהדאטהבייס יחשב לכל שורה את כל מי שרשאי לראות אותה (ויוונסיה ציבורית: כל המורשים), יתרגם אימייל של שיתוף למזהה, וישלח בקשה לכל אחד מהם (כל אחת בקשה ל-Durable Object). בחדר הבית: בקשה אחת לשינוי, וההפצה לכל מי שעל מסך הבית חינם. כל לקוח טוען את המפתח ב-RLS שלו, ומי שלא רשאי מקבל ריק. המחיר: בקשה קטנה אחת אצל מי שלא רואה את השורה, ו-`uuid` של ויוונסיה פרטית שעובר אצלו כסימן, בדיוק כמו מחיקה ב-`postgres_changes` היום ("צד השרת", 4). זה נכון לעשרות אנשים בבת אחת; אם יום אחד יהיו אלפים על מסך הבית, עוברים לחדר לאדם, וזה שינוי בשרת ובטריגר בלבד, לא בקיט.
  - **ההרשאה לחדר הבית:** שאלת ההרשאה של האפליקציה בלי מזהה (בביודנסה `is_allowed()`). בחדר הבית עובר רק `chg`; `txt`, `cur` ו-`rs` נזרקים.
- **גישה שנלקחה:** מחיקה של ויוונסיה, הסרה של בעלים או של שיתוף, וויוונסיה שעברה מציבורית לפרטית מגיעות לחדר שלה עם הסימן `x`. השרת שולח לכל שקע בחדר `reauth`, הקיט עונה מיד ב-`auth` עם הטוקן, ומי שכבר לא רשאי נסגר ב-`4003` בתוך שניות, לא אחרי שעה (שלב 1). במקביל המקורות טוענים את המפתח, השורה לא חוזרת, והאפליקציה עושה מה שהיא עושה היום לדבר שנעלם (`RosterApp.gone`).
- **השלמה ונפילה:**
  - **אחרי כל `ok`** (חיבור, חיבור מחדש, מעבר חדר): כל מקור שהיה טעון לפני שהשקע ירד נטען פעם אחת בשקט (`origin: "sync"`, פרץ, בלי אפקט לפריט). מקור שהטעינה הראשונה שלו התחילה אחרי שהשקע ירד לא נטען שוב.
  - **כשהממסר לא זמין** (אין `ok` אחרי הניסיון הראשון, `4003` או `4004` לחדר, או אדם לא מחובר): כל מקור חי של האפליקציה עובר ל-`stale` ונטען בשקט כל 30 שניות (`T.poll`) כשהלשונית נראית, וגם בחזרה ללשונית. `ok` מחזיר `live` ועוצר את הטעינה החוזרת. **בלי נפילה ל-`postgres_changes`,** מאותן שתי סיבות של שלב 1: לא מפצלים, ולא מחזירים עומס ל-Supabase בבת אחת.
  - **סימן שהלך לאיבוד** (`pg_net` נכשל, ה-Worker לא ענה) לא נשלח שוב. השינוי הבא של השורה או ההשלמה הבאה מביאים אותו. **הכתיבה עצמה לא נפגעת אף פעם:** `pg_net` רק שם בקשה בתור, היא יוצאת אחרי ה-commit, וכתיבה שבוטלה לא שולחת כלום.
- **מה האפליקציה כותבת:** רק `room` על המקורות של דבר פתוח, ו-`keyCol` על כל פריט של `watch` (העמודה בטבלה הנצפית שמחזיקה את המפתח של המקור, למשל `item_id`), כדי ש-`chg` עם `kc` כזה יטען שורה אחת ולא את כל המקור. `watch` בלי `keyCol`: `chg` על הטבלה שלו טוען את כל המקור.
- **צד השרת, לכל אפליקציה שעוברת** (במקום 1 ו-5 של "צד השרת" למעלה):
  1. שורה ברשימת החדרים של ה-Worker: החדר של דבר (מזהה ושאלת הרשאה), חדר הבית (שאלה בלי מזהה), ו-`notify` (`worker/LIVE.md`).
  2. פונקציה בדאטהבייס שממפה שורה לחדר ולמפתח, וטריגר ברמת הפקודה על כל טבלה שמקור קורא או צופה בה, בצורה של `apps/biodanza/relay-notify.sql`. המטען: מזהים ו-`rev` בלבד. שורה של ילד שההורה שלה כבר נמחק (מחיקה מדורגת) לא שולחת: המחיקה של ההורה כבר סימנה לחדר.
  3. הסוד ב-Vault של הפרויקט (`live_notify_secret`) וב-Worker (`LIVE_NOTIFY_SECRET`), אותו ערך. בלי הסוד הטריגר לא עושה כלום והכתיבה עוברת כרגיל.
  4. השם של הסכמה ב-`SUPABASE.relayData` ב-`/supabase.js` ("ניתוק מ-Supabase Realtime").
- **עלות (הערכה, ערב טיפוסי: 3 מנחים, האפליקציה פתוחה כשעתיים, 10 דקות של עריכה משותפת; הפירוט ב-`worker/LIVE.md`):** כ-240 כתיבות של הקיט הן כ-12 בקשות (20 הודעות נכנסות הן בקשה); כ-10 סימנים מהדאטהבייס הם כ-25 בקשות (בקשה ל-Worker ובקשה לכל חדר); כ-50 פתיחות שקע. **שלב 2: כ-90 בקשות לערב, ועם שלב 1 כ-410 מתוך 100,000 ליום (0.4%).** במקרה הגרוע (הכותרת לא עוברת, וכל כתיבה מסומנת גם מהדאטהבייס): כ-1,470 (1.5%). ב-Supabase: שורת תור ושורת תשובה של `pg_net` לכל סימן מהדאטהבייס (10 עד 250 לערב, `pg_net` מנקה לבד), כ-500 טעינות קטנות של שורה, ו-**0 הודעות Realtime** אחרי שלב 3.
- **אסור:** תוכן, אימייל או שם בסימן; טריגר לכל שורה (`for each row`) לסימן; סימן שהאפליקציה שולחת בעצמה; החלה של שורה מתוך סימן בלי טעינה; ושקע שני כדי לשמוע שני חדרים.
- **מה המימוש עשה אחרת (2026-11-26):**
  - **מי מכריז על כתיבה:** הקיט שם `x-floa-live` ושולח `chg` רק כשכל מקור חי של אותה טבלה בלשונית (שקורא אותה או צופה בה) נמצא בחדר של השקע, ולא בחדר הבית. אחרת הכתיבה בלי הכותרת, והדאטהבייס מכריז עליה, כי רק הוא מגיע לכל החדרים של שורה. בביודנסה: הקיט מכריז על הפריטים, המוביל, אפשרויות המוזיקה, הפתיחה ומוזיקת ההתחלה והסיום של הוויוונסיה הפתוחה; `vivencias`, `vivencia_owners` ו-`vivencia_shares` (שייכות לשני חדרים) תמיד מהדאטהבייס.
  - **הכותרת עוברת:** בדיקת CORS אחת מ-`localhost:5173` (2026-11-26) החזירה `x-floa-live` ב-`access-control-allow-headers`, ולכן בקוד אין את הדרך של `prefer`. הטריגר עדיין מכיר את שתיהן. `FLOA_AUTH.api` (`/auth.js`) מקבל עכשיו `opts.headers`.
  - **`chg` של הלקוח:** `kc` הוא ה-`keyCol` של המקור (או של פריט ה-`watch`), המפתחות מהשורות שהשרת החזיר, עם `rev` כשיש (לא במחיקה); מפתח שאינו `uuid`, יותר מ-50, או בלי מפתח: `"*"` בלי `kc`.
  - **קבלה:** `kc` שהוא עמודת המפתח של המקור: השורות האלה (ו-`[מפתח, rev]` שכבר אצלי באותו `rev` נזרק, חוץ ממחיקה); `kc` שהוא עמודה בסינון של המקור: כל המקור, רק כשאחד המפתחות הוא הערך שלי; טבלה ב-`watch` עם `keyCol` שווה ל-`kc`: השורות האלה; כל מקרה אחר או `"*"`: כל המקור.
  - **מעבר חדר:** לחדר של דבר, או לחדר אחר: מיד. ירידה לחדר הבית או לשום חדר: אחרי 10 שניות, כמו השדה האחרון שיצא.
  - **השלמה בחזרה:** גם מעבר חדר מוריד את השקע, ולכן רשימות הבית נטענות פעם אחת בכניסה לוויוונסיה ופעם אחת בחזרה לבית.
  - **בדיקה מקומית (2026-11-26, `wrangler dev` ו-Supabase מדומה):** כתיבה בדף א' מגיעה לדף ב' ב-`chg` ונטענת שורה אחת (כ-510ms, מתוכם 300ms האיחוד של `touch`), אירוע `remote` של `changed` ברשימה; `notify` מדומה מגיע לשני הדפים, וכפילות באותו `rev` לא מביאה אף בקשה; סוד שגוי או חסר 401; חדר ריק 204; `x` גורם ל-`reauth`, ומי שאיבד גישה נסגר ב-`4003` תוך כ-150ms ועובר ל-`stale` עם טעינה חוזרת; חדר הבית מקבל `chg`; ממסר לא זמין: `stale` וטעינה כל `T.poll`; 0 חיבורים ל-Supabase Realtime.

## ניתוק מ-Supabase Realtime
(שלב 3, אותה החלטה של הבעלים. **הצד של הקיט ממומש (2026-11-26):** מקור של אפליקציה ב-`SUPABASE.relayData` לא פותח ערוץ של Supabase, ובלי ממסר הרשימה לא נקראת. ה-SQL לא רץ.)
- **המתג, לכל אפליקציה:** `SUPABASE.relayData` ב-`/supabase.js`, רשימה של סכמות (בהתחלה `["biodanza"]`), ליד `SUPABASE.relay`. למקור שהסכמה שלו ברשימה **הקיט לא פותח שום ערוץ של Supabase Realtime** (לא `phx_join`, לא `postgres_changes`), והנוכחות שלו בלי דרך של שידור. אם אף מקור בדף לא צריך את Supabase Realtime, החיבור הראשי ל-Supabase לא נפתח בכלל. אפליקציה שלא ברשימה ממשיכה בדרך של היום. בלי `SUPABASE.relay` הרשימה לא נקראת, והכול כמו היום: זו הדרך חזרה.
- **ה-SQL:** `apps/biodanza/realtime-off.sql` מוציא את שמונה הטבלאות של ביודנסה מ-`supabase_realtime`, וחוזר ב-`realtime-off.rollback.sql`. **הטבלאות של roster ושל `roster-test` נשארות, תמיד:** הלקוחות של roster עוברים לממסר בלי להוציא אותן, כי אתרים חיצוניים עשויים להאזין להן ("רוסטר ואתרים חיצוניים"). הקובץ מסרב לרוץ כל עוד יש ב-`realtime.subscription` הרשמה של `postgres_changes` לטבלה של ביודנסה, כלומר כל עוד לקוח ישן פתוח איפשהו.
- **הדאטהבייס משותף עם האפליקציה המפורסמת,** והיא עוד מאזינה ל-`postgres_changes` (הנושא `realtime:biodanza`) ושולחת סמנים בנושא הציבורי `biodanza-cur:<id>`. הוצאה מה-publication לפני שהאפליקציה החדשה פורסמה, ולפני שהלשוניות הישנות נסגרו, עוצרת לה בשקט את כל העדכונים החיים. **הסדר הבטוח:**
  1. פריסה של ה-Worker עם הממסר (שלב 1) ועם `/live/notify` (שלב 2), והסוד `LIVE_NOTIFY_SECRET`. האפליקציה הישנה לא מרגישה כלום.
  2. הסוד ב-Vault, הרצה של `relay-notify.sql` והבדיקה שלו. מעכשיו כל כתיבה, גם של האפליקציה הישנה, שולחת סימן לממסר. אין שם אף שקע, וה-Worker זורק אותו בזול. האפליקציה הישנה עדיין על `postgres_changes`, בלי שינוי.
  3. בדיקה מקומית של האפליקציה החדשה מול הממסר הפרוס (שני דפדפנים, שני חשבונות), כולל כתיבה מ-SQL שמגיעה בסימן.
  4. **פרסום של האפליקציה החדשה,** עם `SUPABASE.relay` ו-`SUPABASE.relayData = ["biodanza"]`. בתקופת המעבר שתיהן חיות יחד: כתיבה של הישנה מגיעה לחדשה דרך הטריגר, וכתיבה של החדשה מגיעה לישנה דרך `postgres_changes`, כי ה-publication עדיין שם. סמנים והקלדה חיה לא עוברים בין ישנה לחדשה (נושאים שונים), וזה מקובל לימים ספורים.
  5. **המתנה עד שאין לקוח ישן:** ה-service worker של האפליקציה מתעדכן, ולשוניות ישנות נסגרות. בודקים כמה פעמים לאורך כמה ימים שהספירה ב-`realtime.subscription` לטבלאות של ביודנסה היא 0 (אותה בדיקה שהקובץ עושה בעצמו).
  6. **הרצה של `realtime-off.sql`.** מעכשיו Supabase Realtime לא נושא שום דבר של ביודנסה.
  7. אחר כך, בהחלטה נפרדת: מחיקה של דרך השידור של Supabase מהקוד ושל המדיניות של הערוצים הפרטיים על `realtime.messages`. המעבר של roster מוגדר ב"רוסטר ואתרים חיצוניים", ואין בו ניתוק.
- **חזרה לאחור, בסדר הפוך:** קודם `realtime-off.rollback.sql` (הטבלאות חוזרות ל-publication), ורק אחר כך הוצאה של `biodanza` מ-`SUPABASE.relayData` ופרסום. בסדר ההפוך יש חלון שבו לקוחות מאזינים ל-Supabase לטבלאות שלא שולחות כלום. חזרה משלב 2: `relay-notify.rollback.sql` (מוריד את הטריגרים בלבד).
- **מה לא נמחק בשלב 3:** עמודות `rev` והטריגר שלהן (השמירה המותנית צריכה אותן), המדיניות של הערוצים הפרטיים (עד שדרך השידור נמחקת), ו-`pg_net`.
- **ממתין להחלטת הבעלים:**
  1. פרסום של האפליקציה החדשה עם `SUPABASE.relayData`.
  2. הרצה של `apps/biodanza/realtime-off.sql`, אחרי שהספירה של לקוחות ישנים היא 0.

  - **מה הוא:** מאזין לחדר בלי מקור. הוא משתתף באותו שקע אחד ללשונית (כמו מקור עם `room`), עם אותה הרשאה, פעימה, המתנה שגדלה, סגירה אחרי 30 שניות של הסתרה, ו-`reauth`. אין לו שורות ואין לו טעינה: הדף טוען בעצמו.
