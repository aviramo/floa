# `worker/` — נקודת הקצה של הטופס

האתר סטטי (GitHub Pages) ואין לו שרת. ה־Worker הזה **הוא** השרת, והוא קיים
לצורך אחד: להחזיק את מפתח ה־API של Resend במקום שהדפדפן לא יכול לראות, ולשלוח
את הפנייה במייל.

```
POST https://floa-lead.<החשבון>.workers.dev/lead
{ "business": "floa", "name": "...", "phone": "...", "page": "...", "url": "..." }
->  { "ok": true }
```

**שום פנייה לא נשמרת.** לא כאן, לא ב־Firebase ולא בשום מקום אחר. הפנייה הופכת
למייל וזה כל סיפור חייה.

## Worker אחד, כל העסקים

`business` הוא מי שלח, וזה הדבר היחיד שקובע לאן הפנייה נוחתת: **פנייה של לקוח
מגיעה לתיבה של הלקוח ולעולם לא אלינו.** כל עוד כל העסקים מוגשים מ־floa.co.il,
ה־origin לא יכול להבחין ביניהם, ולכן העסק אומר מי הוא וה־Worker מחפש את הנמען
*שלו*.

`src/businesses.js` **נוצר על ידי `build.mjs`** מתוך `businesses/<key>/index.js`.
אין לערוך אותו. זה מה שמונע את התקלה שקרתה כאן פעם: שם דף שהשתנה באתר ולא ברשימה
של ה־Worker, וכל פנייה ממנו נדחתה בשקט. היום הרשימה נכתבת מחדש באותה בנייה.

בטבלה יש **שם של משתנה סביבה**, לא כתובת מייל. הריפו ציבורי, והתיבה של לקוח לא
נכנסת אליו.

## למה workers.dev ולא api.floa.co.il

`floa.co.il` **אינו** מנוהל ב־Cloudflare. ה־nameservers שלו מצביעים ל־sitesdepot
ורשומות ה־A שלו ל־GitHub Pages. Cloudflare route (למשל `api.floa.co.il/lead`)
תופס רק על זון שמנוהל ב־Cloudflare, ולכן route כזה לא יכול לעבוד כאן. בעבר
`wrangler.toml` אכן הגדיר route על `api.floa.co.il`, מארח שמעולם לא נפתר ב־DNS,
והתוצאה הייתה שכל פנייה נכשלה בדפדפן לפני שהגיעה לשום מקום.

`workers.dev` לא דורש DNS בכלל. הכתובת אינה נראית למבקר — היא רק יעד של fetch
ברקע, וה־Worker דוחה כל origin שאינו `floa.co.il`.

## הגדרה חד־פעמית

### 1. אימות הדומיין ב־Resend

ב־[resend.com](https://resend.com) → **Domains** → **Add domain** → `floa.co.il`.
Resend ייתן שלוש רשומות DNS. מוסיפים אותן **אצל sitesdepot** (שם מנוהל ה־DNS):

| סוג | לְמה זה משמש |
|---|---|
| TXT (SPF) | מרשה ל־Resend לשלוח בשם הדומיין |
| CNAME/TXT (DKIM) | חותם את המייל, כדי שלא ייחשב מזויף |
| TXT (DMARC) | אומר לשרתי היעד מה לעשות עם מייל שנכשל |

בלי זה, מייל מ־`no-reply@floa.co.il` ייחסם או ייפול לספאם. האימות לוקח כמה דקות
עד כמה שעות, תלוי בהתפשטות ה־DNS.

לאחר שהדומיין מסומן **Verified**, יוצרים **API Key** בהרשאת *Sending access*
בלבד.

### 2. פרסום ה־Worker

```bash
cd worker
npx wrangler login
npx wrangler secret put RESEND_API_KEY     # מדביקים את המפתח, הוא לא נכנס לגיט
npx wrangler deploy
```

בסוף הפריסה wrangler מדפיס את הכתובת:

```
https://floa-lead.<החשבון>.workers.dev
```

### 3. לחבר את האתר לכתובת הזאת

ב־`businesses/floa/content/site.js`, `runtime.leadEndpoint` חייב להצביע בדיוק לשם:

```js
leadEndpoint: "https://floa-lead.<החשבון>.workers.dev/lead",
```

ואז `node build.mjs` בשורש, קומיט ופוש. **בלי הצעד הזה הטופס עדיין שולח לכתובת
הישנה ונכשל.**

`LEAD_TO` ו־`LEAD_FROM` יושבים ב־`wrangler.toml` (הם אינם סודות).
**`RESEND_API_KEY` הוא סוד ולעולם אינו בקוד, בריפו או בדפדפן.**

## עסק חדש: לאן הפניות שלו הולכות

ב־`businesses/<key>/index.js` מגדירים `lead.to`, שם המשתנה שיחזיק את התיבה שלו:

```js
lead: { to: "LEAD_TO_DANA", origins: ["https://floa.co.il"] },
```

ואז, פעם אחת:

```bash
cd worker
npx wrangler secret put LEAD_TO_DANA     # dana@example.com
npx wrangler deploy                      # src/businesses.js כבר נבנה מחדש
```

**משתנה שלא הוגדר מפיל את השליחה ב־502 ומדפיס לוג.** זו החלטה מכוונת: פנייה
שנוחתת בשקט בתיבה הלא נכונה היא נזק שאין ממנו חזרה, ופנייה שנכשלת בקול היא באג
שמתקנים.

## `/aum-push`: התראות דפדפן למנהלי AUM

לא נקרא מדפדפן אלא מהדאטהבייס: כש`aum_signup` יוצרת משתתף חדש היא שולחת לכאן (pg_net) את כתובות ה־Push של המנהלים שהפעילו התראות בדף הניהול, וה־Worker דוחף לכל אחת (Web Push, חתימת VAPID, בלי תוכן). אין origin לבדוק, ולכן הטוקן המשותף הוא כל המנעול.

```
node scripts/vapid.mjs                      # זוג מפתחות, פעם אחת
npx wrangler secret put VAPID_PRIVATE       # מדביקים את ה-private
npx wrangler secret put VAPID_PUBLIC        # מדביקים את ה-public
npx wrangler secret put AUM_PUSH_TOKEN      # סיסמה אקראית ארוכה
npx wrangler deploy
```

המפתח הציבורי והטוקן נכנסים גם ל־`aum_settings` בדאטהבייס (ראו סוף `businesses/aum/schema.sql`). את זוג המפתחות עושים פעם אחת: דפדפנים נרשמים מול המפתח הציבורי, והחלפה אחר כך מנתקת את כולם בשקט.

## `/roster/v1/*`: ה־API הציבורי של Roster

האתר של עסק לעולם לא מדבר עם הדאטהבייס. הוא מדבר עם הנתיבים האלה, עם מפתח, וה־Worker הוא הדלת היחידה: הוא קורא רק לפונקציות `roster_api_*` ב־Supabase (`/rest/v1/rpc/…`), עם מפתח ה־service role, ולעולם לא לטבלה. המפתח קובע את העסק ומה מותר; שום מזהה עסק שהקורא שולח לא נחשב. הקוד ב־`src/roster/` (ההנחות על פונקציות הדאטהבייס כתובות בראש `src/roster/db.js`) והבדיקות ב־`test/roster-*.test.js`.

| נתיב | מפתח |
|---|---|
| `GET /roster/v1/meetings` | ציבורי או סודי |
| `POST /roster/v1/signup` | ציבורי או סודי |
| `POST /roster/v1/payments/click` | ציבורי |
| `GET /roster/v1/participants?phone=` ו־`/participants/{id}` | סודי |
| `POST /participants/{id}/registrations`, `DELETE …/registrations/{meeting}` | סודי |
| `POST /roster/v1/payments`, `POST /participants/{id}/pay-from-credit` | סודי |

מפתח ציבורי (`rk_pub_…`) בטוח בדפדפן; סודי (`rk_sec_…`) רק משרת, ובקשה איתו שמגיעה עם `Origin` נדחית. CORS נקבע לפי המפתח, לא לפי הרשימה הגלובלית של `/lead`. גוף עד 16KB, JSON קפדני, כל שגיאה היא `{"error":{"code","message"}}` בלי טקסט מהדאטהבייס.

**אחרי כל פעולה שיכולה ליצור אירוע** (הרשמה, תשלום, ביטול) וגם **כל דקה מהקרון**, ה־Worker מרוקן את תור האירועים (`roster_events_claim`): שולח webhook חתום (HMAC-SHA256 על `t + "." + body`, timeout של 10 שניות, בלי מעקב אחרי הפניות, ה־URL נבדק שוב בכל שליחה) ושולח מיילים דרך Resend, ואז מדווח הכול ל־`roster_events_done`. כשל נרשם ולא עוצר דבר. אחרי webhook שנכשל נסיונות חוזרים אחרי דקה, 5 דקות, חצי שעה, שעתיים ו־12 שעות.

```
cd worker
npx wrangler secret put SUPABASE_SERVICE_KEY   # מפתח ה-service role של Supabase
npx wrangler secret put ROSTER_IP_SALT         # מחרוזת אקראית ארוכה, חובה
npx wrangler deploy                            # מעלה גם את הקרון (wrangler.toml)
```

- **`SUPABASE_SERVICE_KEY` עוקף את כל מדיניות ה־RLS.** הוא סוד בלבד, לא ב־`wrangler.toml` ולא בשום קובץ בריפו. בלעדיו כל נתיב של Roster עונה 503 והקרון לא עושה כלום, ושאר ה־Worker ממשיך כרגיל.
- **`ROSTER_IP_SALT` הוא סוד חובה.** כל מונה לפי כתובת IP (במסד ובקוד) נשמר כ־hash של הכתובת יחד איתו. בלעדיו ה־hash הוא SHA-256 חשוף של כתובת IPv4, ואפשר להפוך אותו בניסיון של כל הכתובות, ולכן כל נתיב של Roster עונה 503 ויש שורת לוג שמציינת מה חסר. כתובת IPv6 נספרת לפי ה־/64 שלה (בעל /64 אחד לא יכול לקבל מונה חדש בכל בקשה). אחרי שמגדירים אותו לא מחליפים אותו בלי סיבה: ההחלפה מאפסת את כל המונים הפעילים.
- `RESEND_API_KEY` הוא אותו סוד שכבר קיים, והוא שולח גם את המיילים של Roster, מהכתובת `no-reply@floa.co.il`.
- **תקרות מייל.** מיילים למשתתפים: 3 לכתובת ביום ו־200 לעסק ביום. מיילים לרשימת ההתראות של העסק: 20 לכתובת ביום ו־30 לעסק בשעה. הכול ביחד: 400 לעסק ביום. המונים מגיעים מהדאטהבייס בכל תור אירועים, וה־Worker תופס את המקום לפני השליחה (לא אחריה), כך ששמונה שליחות במקביל לא עוקפות תקרה. ההזמנות משותפות לכל הרצות התור באותו isolate (כל קריאת API מתחילה הרצה, והקרון עוד אחת), וכל הרצה סופרת מעל המונים שלה את המיילים שהרצות האחרות עדיין שולחות או שדווחו אחרי שהיא התחילה למשוך. בין isolates שונים אין שיתוף, ולכן בהתפרצות שמתפזרת על כמה isolates התקרה עשויה להיחצות במעט, ובכל מקרה העסק לא מקבל יותר מ־120 משתתפים חדשים בשעה מהמפתח הציבורי. מייל שחרג מתקרה נרשם כנכשל עם `limit_*` ובלי תוכן, והאירוע ממשיך.
- **מפתחות שגויים.** בקשה בלי מפתח, עם מפתח פגום או עם מפתח שהדאטהבייס לא מכיר נספרת לכתובת שלה: 60 ב־10 דקות, ואז 429 בלי פנייה לדאטהבייס.
- **תבניות מייל של עסק** מעל 20,000 תווים או עם יותר מ־50 `data-if` לא נטענות: נשלחת תבנית ברירת המחדל ונכתבת שורת לוג `template_rejected`.
- **webhook:** רק HTTPS בפורט 443, ובלי כתובות של שירותי wildcard DNS (`nip.io`, `sslip.io` ועוד). הבדיקה האחרונה ב־Worker היא שלושת הדפוסים של `roster_valid_webhook_url` בדאטהבייס, אחד לאחד, כך שכתובת שעוברת כאן לא תיכשל בשמירה: בלי קו תחתון, בלי נקודה בסוף, בלי אותיות שאינן לטיניות, וסיומת של 2 עד 24 אותיות בלבד (לא `example.c`, לא `xn--p1ai`).
- בדיקות: `node --test "worker/test/roster-*.test.js"` (ב־node בלבד, בלי רשת).

## מה ה־Worker אוכף

| הגנה | מה קורה |
|---|---|
| **Origin** | רק origin שרשום לאותו עסק. אחרת 403 |
| **זהות העסק** | עסק שאינו בטבלה נדחה. עסק אינו יכול לשלוח פנייה בשם דף של עסק אחר |
| **אימות שם** | 2–80 תווים, בצד השרת ולא רק בדפדפן |
| **אימות טלפון** | נייד או קווי ישראלי, מנורמל בצד השרת |
| **אימות שם העמוד** | חייב להיות אחד מדפי אותו עסק. אחרת אפשר היה להזריק כל מחרוזת לשורת הנושא |
| **נמען חסר** | 502 ולוג, לא ניחוש. פנייה לא נוחתת בתיבה הלא נכונה |
| **Honeypot** | שדה נסתר שרק בוט ממלא. מקבל 200 מזויף כדי שלא ינסה שוב |
| **Rate limit** | פנייה אחת לכל 30 שניות לכל כתובת IP |

## בדיקה

```bash
npm test                    # מריץ את worker/test/lead.test.mjs
```

הבדיקה מריצה את ה־Worker עצמו עם Resend מדומה, ובודקת את מה שבאמת אסור שיישבר:
פנייה של לקוח מגיעה ללקוח ולא אלינו, עסק לא יכול לטעון לדף של עסק אחר, ונמען
שלא הוגדר נכשל בקול.

לבדיקה מקומית מקצה לקצה:

```bash
npx wrangler dev            # מאזין על localhost:8787
```

ואז ב־`businesses/floa/content/site.js` מפנים זמנית את `runtime.leadEndpoint`
ל־`http://localhost:8787/lead`, ומריצים `npm run dev` בשורש.

## חשוב

הודעת ה"תודה" מוצגת למשתמש **רק** אחרי ש־Resend אישר שהמייל נשלח. אם השליחה
נכשלה, הדפדפן מקבל שגיאה, השדות **לא** מתנקים, והמשתמש יכול לנסות שוב או לפנות
ב־WhatsApp.
